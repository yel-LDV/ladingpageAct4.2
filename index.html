Sección 01

Introducción a la Gestión de Transacciones

Una transacción representa la unidad lógica de ejecución de un programa que accede y, posiblemente, actualiza diversos elementos de datos.

¿Qué es una transacción?

En los sistemas de bases de datos, una transacción es una secuencia de operaciones de lectura y escritura que se ejecutan como un bloque indivisible. Un ejemplo clásico es una transferencia bancaria: debitar dinero de una cuenta y acreditarlo en otra. Ambas operaciones deben completarse juntas o ninguna de las dos (Silberschatz et al., 2020).

  • COMMIT (confirmación)
  • ROLLBACK (aborto)

Retos principales

El SGBD debe afrontar fallas repentinas de hardware o energía durante la ejecución, así como accesos concurrentes de múltiples usuarios que interactúan simultáneamente con la misma base de datos sin corromper la información (Coronel & Morris, 2019).

Sección 02

Las Propiedades ACID

Conjunto de propiedades fundamentales que garantizan que las transacciones se procesen de manera confiable y segura (Silberschatz et al., 2020).

Atomicidad («todo o nada»)

Principio de indivisibilidad transaccional

O todas las operaciones de una transacción se ejecutan con éxito y se reflejan en la base de datos, o ninguna de ellas lo hace. Si ocurre un fallo a mitad de la ejecución, el SGBD deshace automáticamente todos los cambios realizados (rollback), dejando la base de datos en su estado original.

Ejemplo: al transferir $500 de la cuenta A a la cuenta B, si se debita a A pero el sistema falla antes de acreditar a B, la atomicidad obliga a revertir el débito en A.

Consistencia

Preservación de reglas e invariantes

Una transacción debe transformar la base de datos de un estado válido a otro estado válido, cumpliendo con todas las restricciones de integridad, claves foráneas, tipos de datos y reglas de negocio definidas en el esquema.

Ejemplo: si una regla establece que el saldo total de cuentas nunca puede ser negativo, cualquier transacción que viole esta regla será rechazada.

Aislamiento (Isolation)

Independencia entre transacciones concurrentes

Aun cuando múltiples transacciones se ejecuten concurrentemente, el resultado final debe ser idéntico al que se obtendría si se hubieran ejecutado una tras otra (de forma estrictamente serial). Ninguna transacción puede interferir con los datos intermedios de otra (Elmasri & Navathe, 2016).

Ejemplo: dos usuarios comprando el último boleto de un vuelo al mismo tiempo; el aislamiento garantiza que solo uno de ellos lo obtenga exitosamente.

Durabilidad (Durability)

Persistencia ante fallos catastróficos

Una vez que una transacción ha sido confirmada (COMMIT), sus cambios son permanentes en la base de datos, incluso si se produce un corte eléctrico inmediato o un fallo total del sistema operativo.

Ejemplo: el SGBD escribe los cambios confirmados en almacenamiento no volátil, respaldado por la bitácora de transacciones o por el registro write-ahead log (WAL).

Sección 03

Control de Concurrencia y Anomalías

Cuando varios usuarios operan simultáneamente pueden surgir inconsistencias si el SGBD no regula adecuadamente el acceso a los datos compartidos.

Principales anomalías por concurrencia

  • Lectura sucia (Dirty Read)

    Ocurre cuando una transacción lee datos modificados por otra que aún no ha sido confirmada y que posteriormente puede abortar (rollback).

    Resultado: el proceso lee información falsa o inválida.

  • Lectura no repetible (Non-repeatable Read)

    Sucede cuando una transacción lee un valor y, antes de finalizar, otra modifica ese mismo valor y hace COMMIT. Al releer, obtiene un dato distinto.

    Resultado: inconsistencia en lecturas múltiples dentro de la misma TX.

  • Lectura fantasma (Phantom Read)

    Una transacción ejecuta una consulta sobre un rango de criterios y, mientras tanto, otra inserta o elimina registros que cumplen ese rango.

    Resultado: aparecen filas «fantasma» en consultas repetidas.

Protocolo de Bloqueo de Dos Fases (2PL)

El mecanismo más utilizado para garantizar la serializabilidad en bases de datos relacionales mediante la gestión ordenada de cerrojos (Elmasri & Navathe, 2016).

Fase de crecimiento (Growing)

La transacción puede adquirir nuevos bloqueos (compartidos o exclusivos), pero no puede liberar ninguno hasta completar esta etapa.

Fase de decrecimiento (Shrinking)

La transacción puede liberar bloqueos previamente adquiridos, pero ya no tiene permitido solicitar nuevos cerrojos.

Sección 04

Niveles de Aislamiento y Sintaxis SQL

El estándar SQL define cuatro niveles de aislamiento; cada uno sacrifica rendimiento o concurrencia para eliminar un conjunto de anomalías (PostgreSQL Global Development Group, 2024).

Anomalías permitidas según el nivel de aislamiento (SQL:1999)
Nivel de aislamiento Lectura sucia Lectura no repetible Lectura fantasma
READ UNCOMMITTED Posible Posible Posible
READ COMMITTED No Posible Posible
REPEATABLE READ No No Posible *
SERIALIZABLE No No No

* PostgreSQL implementa REPEATABLE READ como aislamiento por instantánea (snapshot isolation), por lo que tampoco permite lecturas fantasma.

Ciclo de vida de una transacción 
BEGIN;

UPDATE cuentas SET saldo = saldo - 500.00
 WHERE id = 'A';
SAVEPOINT tras_debito;

UPDATE cuentas SET saldo = saldo + 500.00
 WHERE id = 'B';

-- Si ambas operaciones son correctas:
COMMIT;

-- Si algo falla, se revierte todo:
ROLLBACK;
Declaración del nivel de aislamiento 
-- Al abrir la transacción
BEGIN ISOLATION LEVEL
      SERIALIZABLE;

-- O sobre una transacción ya abierta
SET TRANSACTION
    ISOLATION LEVEL
    READ COMMITTED;

-- Revertir solo una parte del trabajo
ROLLBACK TO SAVEPOINT tras_debito;

Regla práctica: a mayor nivel de aislamiento, mayor consistencia pero menor concurrencia. Un sistema bancario suele operar en READ COMMITTED o REPEATABLE READ, mientras que los procesos de cierre contable requieren SERIALIZABLE.

Sección 05

Recuperación ante Fallos (Recovery)

Estrategias y algoritmos implementados por el SGBD para restaurar la base de datos a un estado consistente tras un fallo (Silberschatz et al., 2020).

  • Tipos de fallos

    1. Transaccionales: errores lógicos (saldo insuficiente) o de sistema que abortan una TX.
    2. Del sistema: cortes de energía o fallos de hardware que detienen la memoria volátil.
    3. De medios: daños físicos en discos que destruyen el almacenamiento persistente.

  • Recuperación por bitácora (Log)

    El SGBD mantiene un archivo de registro (Log / WAL) donde anota cada operación de escritura antes de modificar los datos reales en disco. Los registros típicos son <T start>, <T, X, v1, v2> y <T commit>.

  • Puntos de verificación (Checkpoints)

    Mecanismo periódico en el que el SGBD vuelca los búferes modificados de memoria a disco y escribe un registro especial en la bitácora, reduciendo drásticamente el tiempo de análisis tras un reinicio.
